# Tab

Single tab control for `Tabs` / `ManagedTabs`. Selection normally comes from active-tab context. Resolved `variant` / `size` are exposed as `data-variant` / `data-size`; selection via `aria-selected`. System contracts and token theming: [Tabs overview](?path=/docs/docs-tabs-overview--docs).

Trailing content via `slots.end`. Badge **variants** are chosen on `Badge` itself, then composed into the tab — intentional so `Tab` stays Badge-agnostic and any node can fill the slot. ## `selected` vs context (console warning)

Use `selected` for **standalone** chrome (Storybook tables, static previews) **outside** `ActiveTabContextProvider`.

`selected` only forces selected appearance on **that** Tab (`selected || contextMatch`). It does **not** replace active-tab context for the rest of the list. Under a provider that already has an `activeTab`, also passing `selected` can leave **two** tabs selected, and development logs:

> `selected` forces selected appearance on this Tab only; it does not replace active-tab context for the list. Mixing `selected` with an activeTab can leave two tabs selected.

**What to do:** drop `selected` and drive appearance via `value` + the provider; or keep `selected` and render the tab outside the provider.

## Root element

Internally a `<button>`, so you can pass native button props (`id`, `className`, `disabled`, `aria-controls`, …) and they land on that root.

`data-variant` and `data-size` are set from the `variant` / `size` props — values you pass for those attributes are overwritten. Selection API props (`value`, `selected`) and `slots` are not DOM attributes.

## API

`value` is required for selection under the active-tab provider — without it, clicks do not change the active tab.
